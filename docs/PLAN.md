# План разработки Chill Bill

## Принцип

**Сначала — работает, потом — красиво.** Мы не вырисовываем и не стилизуем
интерфейсы на старте. Скелет экранов делаем чистым HTML (семантичные
элементы, минимум классов) — этого достаточно, чтобы проверять сценарии и
быстро двигаться. Стилизация, адаптив, порядок в разметке и a11y — отдельным
этапом в конце. Лендинг — финальный штрих.

Приоритет всегда: **функциональность → корректность → вид**.

## Этап 0 — Фундамент и контракты

Цель: договориться о форме данных и правилах, чтобы дальше работать параллельно.

- Репозиторий и скрипты (pnpm, husky, CI уже есть).
- Заморозить модель данных (`src/models/types.ts`).
- Конвенции (`docs/CONVENTIONS.md`), решения (`docs/DECISIONS.md`).
- Интерфейс репозитория + реализация на localStorage.
- Никакого UI.

**Готово, когда:** типы зафиксированы, репозиторий умеет читать/писать группы и
операции, CI зелёный.

---

## Этап 1 — Ходячий скелет (чистый HTML)

Цель: end-to-end сценарий «создать группу → открыть → добавить операцию»
работает на голом HTML, без единого стиля и с минимальной логикой (заглушки).

- Multi-page сборка Vite: `index.html` (заглушка) + `app.html`.
- Точка монтирования, переключение экранов в памяти (без роутера).
- Store + actions, автосохранение через репозиторий.
- Экраны голыми элементами: «Группы», «Создать группу», «Группа», «Операция».

**Готово, когда:** сценарий проходится руками в браузере, данные сохраняются
в localStorage и переживают перезагрузку.

---

## Этап 2 — Мясо (функциональность)

Цель: вся заявленная функциональность, всё ещё без стилизации.

- Группы: создание, удаление, участники (добавить/удалить).
- Операции: создание, редактирование, удаление; кто платил, сумма, за кого.
- Домен (чистые функции + тесты, можно вести параллельно UI)
- Блок «Баланс» на экране группы.
- Валидация: Σ долей == total и т.п.

**Готово, когда:** все сценарии из прототипа воспроизводятся, домен покрыт
тестами.

---

## Этап 3 — Порядок и полировка

Цель: превратить работающий скелет в аккуратное приложение.

- Единая вёрстка и стили, общие элементы (кнопки, поля, карточки).
- Адаптив и мобильные экраны.
- Порядок в разметке и структуре файлов.
- Пустые состояния, сообщения об ошибках, подтверждения удаления.
- a11y: фокус, лейблы, клавиатура.
- Надёжность хранилища: битые данные, версии схемы.

**Готово, когда:** приложение выглядит и ведёт себя как продукт, а не как прототип.

---

## Этап 4 — Лендинг (финальный штрих)

Цель: входная точка проекта. Делаем последней.

- Статичный `index.html` по макету: заголовок, описание, «Начать», команда.
- Ссылка «Начать» → `app.html`.
- Проверка в прод-сборке (base для GitHub Pages).

**Готово, когда:** лендинг ведёт в приложение, обе страницы корректны в проде.
